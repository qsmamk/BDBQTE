# QTE Vision Debugger

Phase 1 is a Windows x64 visual debugger. It captures desktop frames and reports what the pixel detector sees. It does not generate game input.

`build/` is generated by CMake. The runtime copy of `config.ini` and the `test_frames/` folder are placed beside the executable.

## Build with Visual Studio 2026

In Visual Studio Installer, install **Desktop development with C++**, the MSVC x64/x86 build tools, a Windows 10 or 11 SDK, and C++ CMake tools.

1. Open Visual Studio and choose **File > Open > Folder**.
2. Select `F:\Codex\QTE`. Visual Studio detects `CMakeLists.txt` and configures the x64 project.
3. Select the `QTEVisionDebugger.exe` startup item and the **x64-Debug** or **x64-Release** configuration.
4. Choose **Build > Build All**.

The same project can be configured and built from a Visual Studio Developer PowerShell:

```powershell
cmake -S . -B build -G "Visual Studio 18 2026" -A x64
cmake --build build --config Debug
cmake --build build --config Release
```

The executable locations are:

- Debug: `build\bin\Debug\QTEVisionDebugger.exe`
- Release: `build\bin\Release\QTEVisionDebugger.exe`

The executable expects to find `config.ini` beside itself, or in its current working directory. The loaded config's folder also receives `reference.bmp`, `qtevision.log`, and `debug_frames/`.

## Run and calibrate

Start `QTEVisionDebugger.exe`. On the first launch, inspect and edit the `config.ini` beside the executable. The configured coordinates are relative to the selected monitor's top-left corner, in pixels. `monitor=0` means the first output returned by DXGI enumeration; on multi-monitor systems, verify that it is the intended display.

Set these values for the game's current resolution and UI scale:

- `center_x`, `center_y`: center of the QTE circle.
- `radius`: distance from the center to the ring's middle.
- `ring_thickness`: radial width scanned around that radius.
- `center_roi_x/y/width/height`: small rectangle around the fixed key prompt. Keep it large enough to include the whole prompt, but avoid including unrelated animated UI.

When the prompt is visible, press **F9**. The program saves that center rectangle as `reference.bmp` beside `config.ini` and begins showing `QTE Match`. Press **F11** to save the configured circular scope as `qte_scope.bmp` beside `config.ini`; the magenta circle marks the configured radius and the green cross marks the configured center. Compare the guide with the actual QTE ring to calibrate `center_x`, `center_y`, and `radius`. Use a reference captured while the QTE is visible. If the screen resolution or UI scale changes, adjust the ROI and save a new reference. A matching percentage above `qte_match_threshold` means the current ROI resembles the saved one; it is not an OCR result.

The debugger window starts near the upper-left corner. Move it outside the ring if it covers any part of the QTE, or set `show_window=false` and use the registered function keys. **F8** pauses or resumes vision processing while frame capture continues. **F10** shows or hides the polar ring diagram. **F11** saves the configured QTE scope. **ESC** exits when the debugger window has focus. F8, F9, F10, and F11 are registered as global hotkeys; if another program already owns one, focus the debugger window and use its keyboard shortcut.

## Detection overview

- **DXGI/D3D11 capture:** Desktop Duplication obtains a GPU frame, copies it to one reusable CPU-readable staging texture, and maps the BGRA pixels. A timeout is treated as an ordinary lack of a new frame. An access-lost error recreates the capture resources.
- **ROI:** The center prompt and ring are sampled at configured monitor-relative coordinates. The detector does not scan the whole screen for circles or UI elements.
- **Reference match:** WIC loads `reference.bmp`; each center-ROI pixel is compared with a configurable per-channel tolerance. `QTE Match` is the percentage of pixels within tolerance.
- **White detection:** BGRA channels are read in the correct order. Near-white pixels must pass both a brightness threshold and a channel-balance threshold.
- **Red detection:** Red must exceed a threshold and be brighter than both green and blue by a configurable ratio. Red samples around the ring produce the pointer angle.
- **Target detection:** The ring is sampled at configurable angular and radial resolution. A per-frame median models any continuous white ring/background line. The normal zone is detected first; the smaller, solid perfect zone is then identified as a denser subregion within it, using both configured density thresholds and the local density contrast. These arcs are recomputed from each frame, so their angle is not fixed in code.
- **White loss and candidate:** White-to-nonwhite changes inside the previous frame's detected perfect arc are counted. A candidate is shown only when white loss and red pixels in that target both pass their configured thresholds. It is a visual signal only.

The small diagram is a polar summary rather than a full-resolution screenshot: green marks the detected normal arc, blue the perfect arc, and red the pointer angle. It is intended to show the algorithm's current interpretation.

`White Pixels` and `Red Pixels` count polar sample observations from the ring scan. They are not counts of every unique screen pixel in the ring. `White Lost` counts sample positions that changed from white to nonwhite inside the previous perfect-zone angle range.

## Offline frame mode

Place numbered `.bmp` or `.png` frames in the `test_frames/` folder beside the executable, for example `000001.bmp`, `000002.bmp`, and `000003.png`. Keep the images at the same resolution and use the same monitor-relative ROI values as the captured game. Windows Imaging Component loads the images; no OpenCV dependency is used. The Phase 1 offline reader accepts image sequences, not MP4 files. If the folder is empty, set `[Test] test_mode=false` for live desktop capture or add BMP/PNG frames before starting offline mode.

Set `[Test] test_mode=true` in `config.ini`, or start the program with `--test`. `frame_interval_ms=16` plays roughly at 60 frames per second; `0` processes frames as quickly as possible. Set `loop=true` to repeat the folder. Offline mode uses the same detector as live capture.

## Parameters to tune

The checked-in values `center_x=1295`, `center_y=710`, and `radius=100` match the current QTE layout. Adjust them to match your game capture:

- `[Capture] monitor`
- `[QTE] center_x`, `center_y`, `radius`, `ring_thickness`, and the center ROI rectangle
- `[Vision] white_threshold`, `white_channel_tolerance`, `red_threshold`, `red_ratio`
- `[Vision] normal_density_threshold`, `normal_density_delta`, `perfect_density_threshold`, `perfect_density_delta`, `min_zone_angle_deg`, `max_zone_angle_deg`
- `[Vision] reference_pixel_tolerance`, `qte_match_threshold`
- `[Vision] white_loss_threshold`, `red_pixels_threshold`
- `[Vision] angle_steps` and `radial_samples` control polar scan resolution
- `[Debug] log_level` is 0 (quiet), 1 (state changes/candidates), or 2 (includes pointer events). `verbose=true` enables level 2. `save_frames=true` saves a full BMP when a new trigger candidate appears.

Configuration is checked at startup. An invalid setting or a capture initialization failure is reported with an explanation and, for Windows API failures, an HRESULT.

## Reading the performance numbers

- **Capture Time** measures frame acquisition, GPU-to-CPU copy, and mapping. It does not include waiting for the next display update.
- **ROI Time** is the ring sampling and zone/pointer analysis.
- **QTE Time** is the center reference comparison.
- **Vision Time** is QTE plus ROI processing.
- **Total Time** is capture plus vision for the latest captured frame.
- **Capture FPS** counts frames successfully received from Desktop Duplication (or images processed per second in offline mode).
- **Average** and **Max** are since startup. **P95** and **P99** use a rolling window of recent total frame-processing times; P99 highlights occasional slow frames that an average can hide.

If Capture Time is high, first check the graphics driver and whether another capture tool is using Desktop Duplication. If QTE Match is low during a visible prompt, tighten the center ROI and adjust `reference_pixel_tolerance`. If target zones are absent, inspect the polar diagram and tune the white thresholds and density values. Do not infer a reliable timing signal from a single QTE.

## Validation before any later phase

Run at least **30 QTEs** across several sessions, including target zones at different angles. Save frame sequences when possible and replay them in offline mode. Record false detections, missed zones, pointer-angle stability, white-loss counts, candidate timing, and P95/P99. Adjust configuration and repeat until the visual results are consistent. Phase 1 stops here; do not add input behavior until the visual detector has been reviewed against real captures.
